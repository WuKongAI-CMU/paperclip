# P0 Scope Cut — 2026-05-13

> **Decision summary.** OpenClaw runtime and `dearme-ai-proxy` runtime are **deferred to P1**. The architecture stays. The code stays. The runtime wiring is removed from the P0 paid-beta surface.
>
> Concretely:
>
> - P0 inbound is **web-only**. No iMessage / Telegram / WhatsApp / Slack / Discord / Signal / SMS / Voice. No wake word. No talk mode.
> - P0 voice capture is **web upload + browser MediaRecorder**.
> - P0 sandbox is the **existing Paperclip sandbox**. No per-session Docker workspaces.
> - P0 cron is **Paperclip routines + heartbeats**. No edge cron.
> - P0 outbound is **web-first**: LinkedIn copy-to-clipboard, X via OAuth (when a single channel is ready), email via SMTP/Resend.
> - P0 LLM access is **server calling OpenAI/Anthropic SDKs directly** with one internal key, writing to the existing Paperclip `cost_events` table. No `dm_sk_*` user keys, no proxy executor wiring.
>
> The `packages/dearme-openclaw` package and the SKILL.md generator remain in the repo as **dormant artifacts** (compile, tests pass, no runtime depends on them in P0). The `packages/dearme-ai-proxy` package likewise stays as a **contract artifact** — the `voice-gate.ts` types and tool-binding types it exports are still imported by P0 code, so we keep the package; only the proxy *routes* and *executors* go dormant.
>
> Position preserved: §9.5 (OpenClaw substrate) and §9.6 (tri-substrate) of `PRODUCT-ARCHITECTURE.md` remain canonical as **future state**. They are gated behind explicit revival criteria below.

## 3. What this saves (eng-week estimate, honest)

The savings are **not** the ~75 eng-weeks quoted in `TRI-SUBSTRATE-ARCHITECTURE.md` §10. That number compares OpenClaw integration vs. building 24 channels + voice + sandbox + cron from scratch — work we were never going to do in P0 anyway.

The honest savings are the **integration work we were about to do** to wire OpenClaw and the proxy runtime into the P0 paid-beta path:

| Item | Estimated eng-weeks |
|---|---|
| Wire OpenClaw gateway dispatcher into `approvalRoutes` for Telegram + iMessage inbound, finish `dearme-openclaw-gateway-dispatch.ts` with retry/auth/health behavior, and ship the live-send proof for both channels | 2.0–2.5 |
| Finish `dearme-ai-proxy` runtime: implement `executeOpenAiChat` / `executeAnthropicMessages` / `executeAgentRun` against real provider SDKs, ship `/agent/run` MCP wiring, add `dm_sk_*` key issuance + rotation flow, write the per-user cost-cap enforcer | 1.5–2.0 |
| First-run channel-pairing UX (device pairing code, OAuth-per-channel onboarding flow, "open OpenClaw to add Telegram" copy, error states) | 1.0–1.5 |
| Browser Agent sandbox wire-up via OpenClaw `agents.defaults.sandbox` | 0.5–1.0 |

**Estimated savings: 5.0–8.0 eng-weeks** of focused build work, plus the ongoing maintenance overhead of two new runtime surfaces (gateway dispatcher health, proxy routing tier drift, OAuth token refresh per-channel × N channels).

This is enough to compress paid-beta open from "4–5 weeks" (per `PRODUCT-ARCHITECTURE.md` §9.3) to "2–3 weeks" with the same engineering capacity.

## 4. What this costs

Three product promises get **weaker** in P0:

### 4.1 "Wake up to a team working for you" — softened

Without iMessage / Telegram / WhatsApp inbound, the "team" is somewhere the user has to *open the workbench* to find. The workbench is open by default on the user's laptop, but it's not the same as a notification on the home screen.

**Why this is acceptable for the consultant wedge:** `PRODUCT-ARCHITECTURE.md` §3 names the first wedge as consultants/coaches/freelancers whose channels are LinkedIn / Calendly / email / web — not iMessage. A consultant living in the workbench is consistent with how they already live in Notion / HubSpot / Calendly today. Web-first is the right wedge surface.

### 4.2 Daily "Dear me" letter — delivered by email instead of preferred channel

The §9.5 design had the daily letter sent via the user's `dailyLetterChannel` config (iMessage, Telegram, etc.). P0 sends via SMTP only.

**Why acceptable:** the letter's value is the *content*, not the delivery channel. Email delivery is universal and zero-config for the user. We mark this as "Email + a preview pane in the workbench" so the workbench stays the source of truth.

### 4.3 Voice capture is keyboard-adjacent, not ambient

Browser MediaRecorder requires the user to press a button. OpenClaw voice wake didn't.

**Why acceptable for P0:** the voice profile capture only needs to happen ~3 times per user (initial fingerprint + occasional drift correction). A button-press is fine for that. The "talk to your team while making coffee" experience is genuinely lost in P0 — but that experience is not a buyer-decision driver for consultants. It's a delight feature for creators.

## 5. Revival criteria

Each runtime gets reactivated under specific observed user behavior:

### 5.1 OpenClaw runtime — revive when

- **≥30% of paid users request iMessage, Telegram, or WhatsApp inbound** in the first 90 days of paid beta (measured via in-product "request a channel" survey + support ticket triage), **or**
- **≥3 of the first 10 paying customers are creators** (not consultants), since creators expect mobile-first ambient interaction, **or**
- **first paid user with ≥10 inbound brand opportunities/week** (audience-care load) — Audience Care without inbound triggers is dead weight for them.

### 5.2 `dearme-ai-proxy` runtime — revive when

- **monthly LLM spend exceeds $5K across users** — at that point, prompt-cache routing and per-tier routing pay back the wire-up work in <30 days (cf. `cache-economics.ts`), **or**
- **first enterprise contract requires per-user cost attribution beyond the company-level `cost_events` row** — the proxy's `subscriptionId` side channel is the cleanest path, **or**
- **batch / queue model usage exceeds 30% of total spend** — proxy can route batch traffic to provider batch APIs (50% cheaper) and the wire-up earns out fast.

Each criterion is one specific signal. The team agrees in advance: when one of these fires, revival is *not* a re-debate — it's a sprint.

## 7. What the user sees that's different in P0

Worth stating plainly so we don't ship dissonance:

- The "team" is in the workbench, not on the user's phone.
- Voice capture is a button, not a wake word.
- The daily letter arrives in email + workbench, not on iMessage.
- Outbound channels visible in P0 = LinkedIn (clipboard), X (when single-channel OAuth ships), Email (Resend/SMTP). Other channels show "Coming soon — request access" in the channel picker, which doubles as our revival-criteria signal counter.

The **promise we keep**: a customer who logs in Monday morning sees content drafted in their voice, a list of opportunities with verified emails, a portfolio update they can publish, and a 200-word "Dear me" letter for the day. That's the consultant-wedge product. It works without any of the deferred substrate.

## 8. Riskiest single deferral

The single highest-risk deferral is **Audience Care going dormant**.

The reasoning: every other dormant role (Browser Agent, Health Monitor, Ads Manager) has zero P0 customer expectation. Browser Agent is "advanced", Health Monitor is invisible plumbing, Ads Manager is explicitly P2. But Audience Care touches a real moment — *somebody just engaged with a thing the user posted, and the user's "team" should follow up*. In P0, that follow-up has to come from the user themselves (or from the workbench's polling-based notification, which is delayed and partial).

If the consultant wedge starts succeeding (LinkedIn DMs from prospects, replies to outbound emails, podcast invitations from X), Audience Care being dormant becomes the most-felt gap. Mitigation: ship a polling-based "engagement inbox" in the workbench in week 2 of P0 — same UX surface the OpenClaw event-driven version would have written to, just refreshed every N minutes from the channels that already have inbound (X mentions API, LinkedIn engagement webhook if available, email reply detection). That keeps the workflow alive without OpenClaw, and the path to OpenClaw revival is a transport swap, not a UX redesign.
